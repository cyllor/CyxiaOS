## D1 统一布局字节与固定系统对象地图

### D1.1 超级块：保持 v1 字节基座【基线字节】

统一介质**不引入新超级块版本**。超级块 v1 全部字节按基线 L3828-3833 逐字节保持：

| 偏移 | 字段 | 固定值 |
|---|---|---|
| 0 | magic:u32 | `0x43594653` |
| 4 | version:u16 | `1` |
| 6 | header_len:u16 | `80` |
| 8 | block_size:u32 | `4096` |
| 12 | total_blocks:u32 | `131072` |
| 16 | fs_uuid | 16B，非零 |
| 32 | generation:u64 | 非零，交替检查点 +1 |
| 40 | checkpoint_lsn:u64 | 单调 |
| 48 | log_epoch:u64 | 非零，交替检查点 +1 |
| 56 | bitmap_start:u32 | `4098` |
| 60 | inode_start:u32 | `4102` |
| 64 | data_start:u32 | `4118` |
| 68 | inode_count:u32 | `256` |
| 72 | root_inode:u32 | `0` |
| 76 | crc32c:u32 | 覆盖整 4KiB、自身置零 |
| 80..4096 | 置零 | 全零 |

区域布局不变：0/1 双超级块，2–4097 线性 redo（4096 块），4098–4101 位图（4 块），
4102–4117 inode 表（16 块），4118 起数据区（基线 L3810-3813；参数注册表
`file.layout_starts=[2,4098,4102,4118]`，基线 L8134）。512 MiB / 4 KiB 块 / 131072 块 /
256 inode / 文件≤8 MiB / 内联 extent≤16 不变（I6）。检查点/代际协议沿用 §9.4/§9.5
（I3），现有 `file_media_v0199::probe_snapshot_media_pair` / `preflight_baseline_checkpoint`
原样复用。v2 超级块（112B 头/CRC@108/data_start=4240）仅被只读预检识别，统一挂载路径
对其返回 `Unauthorized`，唯一兼容路径见 D4。

**决策依据**：策略 A 的核心收益是超级块零修订；「只改版本号」陷阱（候选 L54）由
「新增对象走签名清单、超级块字节不动」规避。

### D1.2 固定系统对象地图：4 基线 + 4 新增 = 8 对象【方向已批准】

统一介质的系统对象计数由基线的 **4 修订为 8**（`[SystemObject; N]` 的 N=8）。这是策略 A
批准时明确要求的设计权威修订（提案 §4 边界）：基线 §9.2.1「4 个系统 inode、13 个数据块」
与 §9.5「除 4 个清单系统 inode 外…」的挂载豁免数同步修订为 **8 个系统 inode、151 个
数据块**（13 基线 + 138 新增）。现有 `file_mount_v1` 的 `[SystemObject; 4]` 校验器
**保持不变**（基线-only 卷的既有契约不破坏）；统一卷走新校验器
`file_media_unified_v1::validate_unified_system_map`（8 对象）。

**系统 inode 段：沿用 v2 的 224+ 段**（根=inode0 不变），固定槽位分配如下：

| 对象 | inode 槽 | 块数 | 规范首块 | 位置来源 | 状态 |
|---|---:|---:|---:|---|---|
| SnapshotCatalogStore（快照目录） | 224 | 1 | 4131 | **固定常量** | 新增·golden-vector-pending |
| BootEpochStore | 225 | 1 | 清单指定（规范参考 4118） | 签名清单 | 基线字节（§9.6） |
| SnapshotSlotStore（8 槽镜像） | 226 | 120 | 4132 | **固定常量** | 新增·golden-vector-pending |
| SnapshotProtectionStore（保护状态） | 227 | 1 | 4268 | **固定常量** | 新增·golden-vector-pending |
| SnapshotRequestStore（持久请求） | 228 | 16 | 4252 | **固定常量** | 新增·golden-vector-pending |
| FileReceiptStore v4 | 229 | 7 | 清单指定（规范参考 4119） | 签名清单 | 基线字节（§9.2.1） |
| FileAclStore v1 | 230 | 4 | 清单指定（规范参考 4126） | 签名清单 | 基线字节（§9.2.1） |
| SecurityStateStore v2 | 231 | 1 | 清单指定（规范参考 4130） | 签名清单 | 基线字节（§9.6.1） |
| 保留空槽 | 232–255 | 0 | — | 必须为空（generation=0） | 方向已批准 |

槽位决策说明：
- **225（BootEpoch）与 228（请求对象）沿用 v2 介质身份**，降低迁移映射成本；
- **226/227 原 v2 集群 inode 去除后重新清单化**为 SlotStore/ProtectionStore（见 D1.4）；
- **224 原 v2 系统根目录 inode 退休**：v1 根=inode0，系统对象为隐藏文件、不出现在普通
  目录项中（基线 L3923-3927），不需要独立系统根目录；224 分配给 SnapshotCatalogStore；
- 基线 4 对象的**块数 1/7/4/1 是基线冻结字节**；其 inode 槽与 extent 位置按基线
  L3917-3923 仍由签名可信清单指定——本表给出规范参考布局（黄金夹具用），不是对基线
  4 对象位置的通用 wire 常量。统一校验器对基线 4 对象检查：固定槽位（上表）、块数、
  `first_block ≥ 4118`、边界、唯一性、与所有对象块范围互斥；
- 新增 4 对象的位置是**固定常量**（4131/4132/4252/4268），签名清单必须精确携带，
  校验器精确验证（fail-closed）。新增块数：目录 1 + 槽 120 + 请求 16 + 保护 1 = 138。

**业务 inode/extent 边界**：业务 inode = **0–223（224 个，含根 inode0）**，与 v2 业务
inode 数一致；系统段 224–231（8 个）；232–255 保留空槽（挂载全量扫描须验证其为空闲
格式：保留 magic/generation=0/CRC，其余为零）。inode 表前 14 页（4102–4115）恰为
224×256B=57344B 业务 inode，后 2 页（4116–4117）为系统/保留段。

**FIRST_BUSINESS_BLOCK 等价物**：统一布局**不设通用硬常量**（基线 4 对象位置清单可变，
不同于 v2 的全固定地图）。规范参考布局下业务数据自 **4269** 起；生产归属由位图/extent
确定性账本核验（extent 物理范围限 `[4118, 131072)`，基线 L3994），位图事务闭包沿用
基线（数据/位图/inode 同事务提交，保留区位图始终已分配）。v2 的 8354 硬常量不沿用。

**挂载豁免与唯一性**：统一挂载全量扫描豁免上表 8 个清单系统 inode，精确验证位置、
块数、代际与唯一性（inode/kind/块范围三重互斥）；其余非根在用 inode 恰有一个可达
目录引用且代际一致（§9.5 模式，豁免数 4→8）。

### D1.3 快照槽几何【方向已批准·几何沿用 v2】

- 8 槽固定 = 6 周期 + 2 按需，不互借（候选 §3）；
- 每槽 **15 块 = 1 描述页 + 14 inode 镜像页**（v2 步长 15 原样沿用）；8×15=120 块，
  槽 i 描述页 = 4132+15i，镜像页 = +1..+14；
- 镜像内容 = **业务 inode 0–223 的 14 页**（57344B）；系统段 224–231 与保留段
  232–255 **永不入镜像、永不被恢复触及**（v2 规则「业务快照和恢复不触及系统 inode」
  沿用）；恢复只替换业务 inode 页与业务视图，系统对象按 D6 合并规则处理；
- 描述页/镜像页的字段级布局（SHA-256 完整性摘要 + CRC32C 结构校验的 v2 模式沿用）
  为 golden-vector-pending；同槽代际镜像不再改变、延长保留只改目录的保护语义沿用。

### D1.4 集群保留去除与容量归还【方向已批准】

- v2 集群保留 = inode 226/227 + 2×2048 块（4242–8337，**16 MiB**）+ 系统根目录
  inode224/块 4240。统一介质**不继承任何集群保留**：v1 基座本无集群概念；
- inode 226/227 重新清单化为 SlotStore/ProtectionStore（D1.2）；inode224 退休改作
  CatalogStore；v2 系统根目录不再需要（根=0，系统对象隐藏）；
- **容量归还**：迁移重建的新镜像中，原 16 MiB 集群块不再被任何对象占有，归业务/快照
  CoW 账本自由容量（新镜像位图除固定系统对象/保留区外全零）。集群文件内容**不是业务
  数据，不导入**；
- **历史保护义务不随之删除**（I4）：BootEpoch 对象原样保留（inode225，计数不回退、
  缺失不得重建归零，基线 L4049-4065）；v2 卷的保留期/保护代际/请求水位经 D4 连续性
  证明迁入新对象载体；
- 业务 inode 容量由基线-only 卷的 252（256−4）变为统一卷的 224（0–223）：这是沿用
  224+ 系统段与 14 页槽几何的批准代价，由 16 MiB 块容量归还补偿；如实登记，不隐性扩容。

### D1.5 新增对象信封【方向已批准·字段 golden-vector-pending】

新增 4 对象沿用基线系统对象信封模式（§9.2.1「为每个对象写入 magic/版本/UUID/代际/CRC」；
BootEpochStore §9.6 的 40B 头模式）。每个对象首块为 **40B 信封 + 全零载荷**（字段布局
冻结前载荷必须为零，fail-closed）：

| 偏移 | 字段 | 值 |
|---|---|---|
| 0 | magic:u32 | 按对象：Catalog `0x43594143` / Slot `0x43594C53` / Request `0x43595152` / Protection `0x43594450` |
| 4 | version:u16 | `1` |
| 6 | header_len:u16 | `40` |
| 8 | fs_uuid | 16B，与超级块一致且非零 |
| 24 | object_generation:u64 | 非零，单调 |
| 32 | crc32c:u32 | 覆盖整 4KiB、自身置零 |
| 36 | reserved:u32 | `0` |
| 40..4096 | 对象字段 | **冻结前必须全零**；字段布局见 D6 与后续黄金向量交付 |

魔数已核对不与现有任何 u32/u64 魔数冲突（含 ResetProof v1 `0x43595250`、ControlRPC
`0x43594351/2`、trial permit `0x43595450` 等）。多块对象（Slot 120 块、Request 16 块）
仅首块携带信封；其余块内容校验为 golden-vector-pending。基线 4 对象载荷仍由各自既有
编解码器校验（boot_epoch_v1 / file_index_v0199 / file_receipt_store_v0199 / ACL），
统一契约层不重复定义其字节。

## D2 0x50 快照端点 ABI 与能力位

### D2.1 端点与封包【方向已批准】

- **不新增系统调用号**（I7，19 个不变）。快照协议走既有 **SVC 0x50 service_call** 下的
  **独立受保护端点**：EL1 单独登记的 endpoint_cap（与 FILE_SERVICE 端点 cap 分离），
  静态判别 = v4 帧 magic `0x43594651` + abi=4 + **op ∈ 0x20..0x2B**（与 FILE_SERVICE
  op 1..15 不相交；FILE_AUTH 以 magic/长度判别的既有模式相同）；
- **不得复用** FileServiceSchemaV2（magic `0x43594632`、64B 头、SVC 0x45 op 寄存器
  0x50、x0=能力索引/x2=能力代际）：旧封包按 §13.6 拒绝（E_SCHEMA/E_STALE），旧 ABI
  仅作迁移参考（候选 L52）；
- 寄存器绑定**沿用 §9.6.1**（基线 L4090-4092）：x0=endpoint_cap、x1=请求帧、x2=总长、
  x3=调用者私有 cap_selector、x4=应答缓冲、x5=容量。op 0x20..0x29 要求 x3≠0（快照
  能力选择子，EL1 查表）；op 0x2A/0x2B 要求 x3=0（身份门，见 D2.3）；
- 请求头 = FileServiceRequest v4 32B 头（D3），请求总长 ≤ **1024B**、应答总长 ≤
  **2048B**（V18 界沿用，严于 v4 通用界 65580/65664）；全部 checked 长度、精确结尾、
  输入输出不重叠、未知 op/非零保留在副作用前拒绝。

### D2.2 12 个语义类与能力位【方向已批准·布线 golden-vector-pending】

op 标签沿用 v2 语义编号（迁移映射一一对应），承载于 v4 op:u16 字段：

| op | 语义类 | 所需快照能力位 | 附加门 |
|---|---|---|---|
| 0x20 | CREATE | CREATE | 当前 live_view_epoch |
| 0x21 | EXTEND | EXTEND | 保留只能延长 |
| 0x22 | DELETE_EXPIRED | DELETE_EXPIRED | 到期+引用+GC 条件+周期保护下限 |
| 0x23 | RESTORE | RESTORE | 当前 live_view_epoch + 恢复证明 |
| 0x24 | LIST | LIST | — |
| 0x25 | QUERY | LIST | — |
| 0x26 | HISTORY_OPEN | HISTORY_READ | UUID+规范路径前缀绑定（组件边界+摘要） |
| 0x27 | FREEZE_SET | PROTECTION | — |
| 0x28 | FREEZE_CLEAR | PROTECTION | — |
| 0x29 | OPEN_WRITES | PROTECTION | 当前 live_view_epoch + 恢复完成证明 + 当前保护代际 |
| 0x2A | QUERY_REQUEST | （身份门） | 原持久主体或已准入恢复监督者 |
| 0x2B | ACK_REQUEST | （身份门） | 原持久主体或已准入恢复监督者 + 终态摘要 |

**能力位分配**：快照管理权位于**独立 snapshot_cap 字（u32）**，与文件权利字
（CapabilityRightsSchema v3 bit8..14）结构性分离，普通 FILE_READ/WRITE/UNLINK 及
ALL_RIGHTS **永不隐含**管理权（I8）：

| 位 | 能力 | 位 | 能力 |
|---|---|---|---|
| bit0 | CREATE | bit4 | LIST |
| bit1 | EXTEND | bit5 | HISTORY_READ |
| bit2 | DELETE_EXPIRED | bit6 | PROTECTION |
| bit3 | RESTORE | bit7..31 | 保留，必须为 0 |

**角色白名单（真实主体，EL1 核验，非封包自报）**：
- 普通主体登记 ⊆ {CREATE, EXTEND, DELETE_EXPIRED, LIST, HISTORY_READ}——**不得**签发
  RESTORE/PROTECTION（V18 grant_snapshots 边界沿用）；
- 恢复监督者登记 ⊆ {LIST, RESTORE, PROTECTION, HISTORY_READ}——独立可信授予入口，
  **不得**占用普通按需创建槽（不得 CREATE）；
- 内部定时维护角色 ⊆ {CREATE, EXTEND, DELETE_EXPIRED, LIST}——无公共签发者，周期保护
  在 AI_DISABLED 下独立推进（候选 §4）；
- 权限原子门、恢复代际字段与黄金反例（越权/旧代际/伪造身份）属 D7 交付。

## D3 FileServiceRequest v4 / Reply v3 绑定

### D3.1 承载方式【方向已批准】

- 快照操作走 **0x50 下独立端点 + v4 32B 头**（magic `0x43594651`、abi=4、header_len=32、
  op:u16、flags:u16=0、payload_len:u32、request_id:u64、auth_context_id:u64=0 由 EL1
  内部封装；基线 L4090-4096），**不是** FILE_SERVICE 端点 op 段扩展——文件端点解码器
  op 1..15 闭包不变（`file_service_v4` 不修改）；
- 应答 = **Reply v3**（magic `0x43594652`、version=3、128B 头、≤65664B；快照应答实际
  ≤2048B）；状态机沿用 v3（UNKNOWN 不得宣称成功）；旧 SchemaV2 封包 E_SCHEMA/E_STALE；
- CREATE/RESTORE/OPEN_WRITES 的 payload 携带当前 live_view_epoch，其余 op 该字段为 0
  （V18 规则沿用）；字段级 payload 布局 golden-vector-pending。

### D3.2 持久/易失划分与去重【方向已批准·分区候选沿用】

- **持久请求**（消耗 SnapshotRequestStore 记录 + 持久票据模式）：CREATE、EXTEND、
  DELETE_EXPIRED、RESTORE、FREEZE_SET、FREEZE_CLEAR、OPEN_WRITES（7 个变更类）；
  按真实主体+代际去重：同键同摘要返回原状态，同键异摘要拒绝，UNKNOWN 不重做（候选 §2）；
- **易失/只读**：LIST、QUERY、HISTORY_OPEN 不消耗持久票据；QUERY_REQUEST/ACK_REQUEST
  以 payload 携带目标持久键（头 request_id 匹配局部 ID，x3=0），ACK 验证原主体与终态
  摘要，不回收 PENDING/UNKNOWN；
- 请求分区沿用 V18 候选：**64 条 = 48 普通 + 8 维护 + 8 恢复**，16 主体水位；
  FileReqKey 36B（UUID+client slot+client generation+request seq）与 SnapshotKey 40B
  （UUID+snapshot_id+slot+reserved+slot generation）作为候选输入沿用，精确布线待锁定；
- 普通 WRITE 不消耗持久票据（基线 §9.6.1 不变）。

### D3.3 staging 预算【方向已批准】

快照帧**复用** v4 staging 纪律：每槽 17 页=69632B，输入消费且冻结摘要/引用后复用为
输出，每组≤1、全局≤8 槽=**544 KiB 计业务 RAM 总账**（基线 L4096-4100）；不新设池，
失败不占完成/恢复池（I5）。快照帧 ≤1024B/≤2048B 远小于槽容量，无额外 staging 需求。

## D4 迁移证明要求（v2 → 统一卷唯一兼容路径）

**唯一路径【方向已批准，基线 I2 强制】**：离线只读导出 → 全零 512 MiB 新镜像重建 →
导入 + 连续性证明。禁止在位重解释、禁止无证明可写迁移、禁止静默重格式化旧卷。

1. **只读导出**：经 `crates/prototype/src/storage.rs` v2 解码 + 快照管理器只读路径导出
   业务数据、快照槽镜像、目录/控制状态、保留期、保护代际、请求水位、BootEpoch 计数。
   v2 解码器已显式拒绝 v1（storage.rs:250-252），v1 解码器拒绝 v2——两侧 fail-closed 不变；
2. **重建**：精确 512 MiB 全零新镜像经格式化器按 §9.2.1 发布顺序初始化：位图/inode 表/根/8 系统对象 → FLUSH → 日志清零 →
   FLUSH → 双份相同初始超级块（generation=1/log_epoch=1/checkpoint_lsn=0）；
3. **导入连续性证明（逐项不回退，I1/I3/I4）**：
   - fs_uuid 一致（身份不符 → Conflict）；
   - BootEpoch 计数：新 ≥ 旧；对象缺失/核验失败不得重建归零（§9.6）；
   - SecurityState 各代际（state/rule_min/security_min/key/service）：新 ≥ 旧；
   - protection_generation、live_view_epoch：新 ≥ 旧；
   - 每槽 slot_generation：新 ≥ 旧；旧槽在用（generation>0）而新槽为空 → 拒绝（历史
     丢失）；同代际保留截止只能延长（新 ≥ 旧）；代际前进时截止仍不得短于旧值（保守
     fail-closed；已证明的 DELETE_EXPIRED  discharged 记录属后续迁移协议交付）；
   - snapshot_id 水位、请求水位：新 ≥ 旧；
   - ACL/inode 代际/持久收据合并：确定性规则由 D6 定义；**恢复业务根时不得导入旧
     FileStreamIndex v4 / SecurityState v2**（台账 S3）；无法证明授权一致 → 拒绝恢复
     （候选 §5）；
4. **拒绝规则**：混合格式/身份不符/代际不连续双份 → RECOVERY_REQUIRED/Conflict
   （`file_media_v0199::probe_snapshot_media_pair` 现状）；任何一项无法证明 → 禁止可写
   迁移，保持只读诊断/镜像导出；
5. 离线恢复程序的重建协议与验收**独立交付**（基线 L3984-3988），不在本件声称完成。

契约层 `check_migration_continuity` 实现第 3 项的逐项单调性校验（纯比较，无字节发明）；

## D6 保护状态载体与合并规则

### D6.1 载体决策：独立 SnapshotProtectionStore【方向已批准】

- 保留期/保护代际/写门/开门证明的持久载体 = **独立 SnapshotProtectionStore**
  （inode227，1 块，首块 4268，D1.5 信封）；
- **不得**写入 SecurityStateStore v2 保留区（248..4095 必须为零，基线 L4609）；
  **不采用** SecurityStateStore v3 修订（避免扩大冻结面）；
- 字段规划（golden-vector-pending）：每槽保留截止[8]、protection_generation、
  write_gate、live_view_epoch、restore_phase、开门证明摘要、保守在线年龄。全部更新走
  完整块 redo 事务，单调不回退（I1/I4）；
- SnapshotCatalogStore 承载槽目录（身份/状态/摘要/snapshot_id 水位）；控制状态中
  保护语义部分归 ProtectionStore，目录语义部分归 CatalogStore——v2 FSControl+Catalog
  的保护职责按此拆分，不得双写。

### D6.2 恢复合并规则【方向已批准】

- 恢复只替换业务 inode 页（0–223）与业务视图，发布新 live_view_epoch；系统 inode
  永不入镜像/恢复（D1.3）；
- ACL/inode 代际/持久收据合并：确定性规则——inode 代际取不回退值、ACL 持久属主以
  签名卷清单为准、持久收据按原键查询终态；**无法证明授权一致 → 拒绝恢复**（候选 §5）；
  禁止恢复普通业务数据导致旧授权复活；不得导入旧 FileStreamIndex v4/SecurityState v2
  （台账 S3）；
- **恢复后写门保持关闭**；只有同时满足（a）真实恢复完成证明、（b）当前保护代际、
  （c）独立 PROTECTION 权限的确定性 OPEN_WRITES 路径才能开门；不依赖模型或自动重启；
  ACK 恢复结果不解除仍存在的保护门（候选 §5；V18 记录 L86-89）。契约层
  `open_writes_gate` 实现三条件原子门。
