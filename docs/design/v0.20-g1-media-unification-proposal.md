## 1. 具体冲突：两套**不是同一可写格式**的介质

候选 §6 已明确判定：「二者**不是同一可写格式**」（候选 L54）。目标 §6 进一步记录：
「生产挂载仍为 V0.18 v2 介质；V0.18 v2 介质及历史快照 ABI 与 V0.19.9 的 v1 基础介质、
FileServiceRequest v4/Reply v3 和授权链存在不兼容差异，v1+快照统一布局须先完成 G1 冻结，
不得发明新格式或以旧卷直接重格式化绕过」（目标 L76）。本节给出该判定的逐点证据。

### 1.3 冲突为何不可调和（不能只改版本号或混读偏移）

1. **固定偏移语义对撞**：块 4118 在 v2 是 FSControl、在 v1 是数据区首块；4119 在 v2 是
   SnapshotCatalog、在 v1 是普通数据；4120–4239 在 v2 是 8 槽镜像、在 v1 是普通数据。
   v1 的 4 个系统对象（自 4118 起的 13 块清单 extent）与 v2 的控制/目录/槽区**物理重叠**。
   任何「混读两套固定偏移」都会把快照元数据当业务数据、或把业务数据当系统对象。
   （证据：§1.1/§1.2 各行；候选 L54「不能只改版本号、混读两套固定偏移或静默重新格式化旧卷」。）
2. **data_start 相差 122 块**（4240 vs 4118）：extent 物理范围、位图归属、redo home 边界
   全部依赖该值（`storage.rs:433` 的 extent 边界校验、基线 L3994「extent 限 data_start 至末尾」）。
   两套卷的同一物理块号指向不同逻辑对象，不存在保持字节不变的可写重解释。
3. **超级块头不兼容**：112B 头/CRC@108/version=2 vs 80B 头/CRC@76/version=1；两侧解码器
   互相 fail-closed（`storage.rs:250-252`；`file_media_v0199.rs:100-127`）。
4. **inode 语义不同**：v2 业务 0–223/系统 224–255 且含集群 inode 226/227（16 MiB 集群日志
   保留）；v1 根=inode0 + 4 个清单系统 inode，无集群概念。集群依赖必须去除，但历史保护
   义务不得随之删除（候选 L54；台账 S5）。
5. **授权链/ABI 不同**：v2 快照走 `FileServiceSchemaV2`（magic `0x43594632`、version=2、
   64B 请求头、SVC 0x45 op 寄存器 0x50、x0=能力索引/x2=能力代际，V18 ABI「Transport and
   compatibility」）；基线走 `FileServiceRequest v4`（magic `0x43594651`、abi=4、32B 头、
   0x50 FILE_SERVICE endpoint_type、x0=endpoint_cap/x3=cap_selector，基线 L4090-4096）+
   Reply v3 + ADMIT v3（基线 L5945-5953、L1086-1088）。候选明确：历史 SchemaV2/SVC 0x45
   「不能直接充当新版 Syscall ABI、FileServiceRequest v4 或 Reply v3」（候选 L52）。
6. **保护状态载体不同**：v2 的保留期/保护代际/写门在 FSControl+Catalog；v1 的代际单调性
   在 SecurityStateStore v2（基线 L4603-4609；`file_index_v0199.rs:288-295`）。恢复业务根
   时不得导入旧 FileStreamIndex v4/SecurityState v2（台账 S3）；ACL/inode 代际/持久收据的
   合并「必须由 G1 统一介质契约定义，无法证明授权一致时拒绝恢复」（候选 §5）。

**结论**：G1 必须先冻结一个统一的新版本化介质布局 + 0x50 快照端点 + 预算核算，
之后才允许任何实现（目标 L76；台账 S5→S6 依赖链）。本提案以下部分均为候选，未冻结。

## 3. 候选统一策略（2–3 个，均为提案，未选定）

### 策略 A：v1 字节基座 + 快照目录/槽作为**新增清单系统对象**（推荐，见 §4）

**思路**：保持超级块 v1 字节布局与 data_start=4118 不变（基线 L3828-3833），redo/位图/
inode 表区域不变；在数据区内由**签名可信清单**追加固定系统对象：SnapshotCatalogStore、
SnapshotSlotStore（8 槽镜像）、SnapshotRequestStore、SnapshotProtectionStore（保留期/保护
代际/写门的持久载体），与既有 4 对象一样「不出现在普通目录项中、挂载全量检查豁免并精确
验证位置和唯一性」（基线 L3923-3927 模式）。业务 CoW 数据使用业务数据区，块所有权/引用/
位图同一确定性账本核验（候选 §2）。v2 旧卷仅经**离线只读导出 → 全零新镜像重建 → 导入+
连续性证明**加入（I2）。

- **优点**：与已批准基线字节兼容面最大；现有 `file_format_v1` 格式化器、`file_mount_v1`
  校验、`file_media_v0199` 预检可复用并有界扩展；超级块无需新版本号，避免「只改版本号」
  陷阱（候选 L54）；与目标既定方向「v1+快照统一布局」（目标 L76）一致。
- **代价/风险**：基线 §9.2.1 冻结的是「4 个系统 inode、13 个数据块」，挂载扫描豁免数也
  按 4 对象写死（基线 L3990-3992；`file_mount_v1.rs:110` 的 `[SystemObject; 4]`）。追加对象
  **必须经设计权威修订基线 §9.2.1/§9.5 与挂载契约**，不是本提案能自行冻结的。槽镜像
  （8×14 页）+目录+请求+保护对象的固定 extent 地图、系统 inode 槽位分配（是否沿用 224+
  段）须重新清单化。SecurityStateStore v2 的 248..4095 保留区必须为零（基线 L4609），
  保留期/保护代际**不能暗增字段**，只能独立对象或经批准的 v3 修订。
- **对不变量**：I1/I4 由独立保护对象+单调事务满足；I2 天然满足（无在位重解释）；I3 复用
  v1 检查点协议；I5 需把 V18 的 68/128/48 KiB 重新落账（见 D5）；I6/I7/I8 不变。

### 策略 B：新版本化超级块（候选标签 v3）+ 显式布局目录 + 验证过的迁移协议

**思路**：定义新超级块版本（候选 v3，扩展头，例如 128B），显式携带 data_start、系统对象
目录指针、快照目录/槽参数与布局 CRC；0/1 双份、redo/位图/inode 区域沿用 v1；数据区自
4118 起但带固定保留地图（4 基线对象+快照对象）；v1/v2 仅保留只读解码，v3 是唯一可写统一
格式；配套离线导出导入**或**满足完整连续性证明的验证迁移（候选 L54 允许后者）。

- **优点**：单一权威、显式版本化，布局自描述，未来扩展不再依赖隐式清单；迁移协议可一次
  冻结、机器可验证。
- **代价/风险**：冻结面最大——新超级块字节、新编解码器、新黄金向量、新状态机全部要从零
  冻结（基线 §13.6 G1 交付清单，L5957-5960）；基线 v1 字节是已批准规范，v3 只能作为经批准
  的**后继版本**而非「发明新格式」（目标 L76）；data_start 仍须 4118，故相对 A 并无字节
  兼容收益，却多出整套超级块迁移证明；与「不能只改版本号」的告诫张力最大，须证明版本
  变化伴随真实布局契约而非绕过。
- **对不变量**：I1–I9 均可满足，但 I2/I3 的证明义务显著重于 A（新旧两代检查点链共存）。

### 策略 C：以 v2 为基座，把 v1 安全对象 graft 进 v2 系统区（反向统一）

**思路**：保留生产 v2 挂载/快照管理器（`journal.rs:203`、`snapshot/manager.rs`），用
BootEpoch/Receipt v4/ACL/SecurityState v2 替换 v2 的集群保留（226/227、2×2048 块），
超级块仍 v2/4240。

- **优点**：复用现成生产挂载与 COW/保留/GC 实现，代码改动面最小。
- **代价/风险**：**直接违反已批准基线**——§9.2/§9.2.1 冻结 v1 字节与 data_start=4118
  （基线 L3828-3833、L3921-3923），§9.6.1 要求「保持 inode/superblock/redo 介质 v1 字节
  布局」（基线 L4069）。采用 C 等于整体重写基线介质章，须设计权威明确推翻 v1 基座；
  候选与目标均以 v1 为规范基座（候选 L54；目标 L76），C 与既定方向相反；且 v2 介质身份
  注释禁止改名（`storage.rs:26-41`），graft 会破坏现有 extent/位图依赖。**不推荐**，
  仅作为完整三选一列出。
- **对不变量**：I6 的 v1 字节子项、I2 的「离线重建新镜像」路径均被破坏，除非基线被修订。

### 3.1 权衡矩阵（提案评估，非冻结结论）

| 维度 | A：v1+清单对象 | B：v3 显式目录 | C：v2 graft |
|---|---|---|---|
| 与已批准基线字节兼容 | 高（超级块不变） | 中（区域不变、头变） | 低（违反 v1 冻结） |
| 需设计权威修订的范围 | §9.2.1 对象数/挂载豁免 | 新超级块+迁移协议+§9.2 | 整个介质章 |
| 冻结/黄金向量工作量 | 中 | 高 | 高（且推翻基线） |
| v2 旧卷兼容路径 | 离线导出导入（I2） | 离线或验证迁移 | 在位 graft（I2 风险） |
| 复用现有代码 | 格式化器/挂载/预检 | 预检+部分挂载 | 生产挂载/快照管理器 |
| 与目标既定方向一致 | 是（目标 L76） | 部分 | 否 |
| 主要残留风险 | 清单对象数修订、保护状态载体 | 双代检查点证明 | 基线合法性 |

## 4. 推荐：策略 A + 离线导出导入作为唯一 v2 兼容路径

**推荐策略 A**，理由：

1. **方向一致性**：目标已把统一目标表述为「v1+快照统一布局」（目标 L76），候选以 v1 为
   规范基座（候选 L54）。A 是该方向的最小增量实现，不发明新格式、不只改版本号。
2. **字节兼容面最大**：超级块 v1、redo/位图/inode 区域、data_start=4118 全部不动，
   已交付的第四波格式化器契约层与挂载校验（目标 L70）可复用，冻结与取证成本最低。
3. ** fail-closed 现状可延续**：现有只读预检已能区分 v1/v2 且拒绝混读/不连续
   （`file_media_v0199.rs:201-239`），A 只需在其上增加清单对象校验，无需新的代际共存证明。
4. **兼容路径合法**：v2→A 不存在保持字节的可写重解释（§1.3），离线导出导入是基线与候选
   唯一明确允许的路径（基线 L3931、L4071；候选 L54；V18 记录 L67-70 已有先例且无一键迁移器）。

**推荐的边界（必须同时批准，否则 A 不成立）**：

- A 不是「零修订」：追加系统对象要求设计权威修订基线 §9.2.1 的对象计数/挂载豁免与
  `file_mount_v1` 的 `[SystemObject; 4]` 契约（`file_mount_v1.rs:110`）。该修订是 G1 冻结
  的前置批准项，本提案无权自行生效。
- 保留期/保护代际不得暗增进 SecurityStateStore v2 保留区（基线 L4609）；推荐独立
  SnapshotProtectionStore 对象，或经批准的 SecurityStateStore v3 修订（二选一，见 D6）。
- 集群保留（226/227、2×2048 块≈16 MiB）去除后释放的容量归业务/快照账本，但 BootEpoch
  等历史保护义务原样保留（候选 L54；I4）。
- 在 G1 冻结前，A 的任何数值（对象块数、inode 槽位、端点 op、能力位）都只是候选输入。

## 5. G1 必须冻结的精确决策清单（冻结前均为开放项）

> 下列 D1–D7 是 G1 的冻结交付物清单（对应基线 §13.6 G1 交付，L5957-5960；候选 §6；
> 台账 S5/S6）。每项给出**必须回答的问题**与**候选默认**（默认仅服务讨论，未冻结）。

### D1 统一布局字节（layout bytes）
- 统一布局的版本标识与超级块决策：A 候选默认=保持 v1 字节（version=1/header_len=80/
  data_start=4118/CRC@76）；若选 B 则须冻结新头全部偏移。
- 数据区固定保留地图：4 基线对象 + SnapshotCatalogStore + SnapshotSlotStore(8 槽×(1 描述
  +14 inode 页)) + SnapshotRequestStore + SnapshotProtectionStore 的**块范围与 inode 槽位**，
  由签名清单固定（基线 L3917-3927 模式）；业务 inode/extent 边界与 FIRST_BUSINESS_BLOCK
  等价物；位图事务闭包（候选 L54）。
- 系统 inode 槽位分配（是否沿用 v2 的 224+ 段；根=0 不变）；集群 inode 226/227 与
  2×2048 块保留的去除方式及容量归还账本。
- 挂载全量扫描的对象豁免数与唯一性校验（修订 `[SystemObject; 4]`，`file_mount_v1.rs:110`）。
- 黄金镜像 + 合法/非法 CRC/摘要向量（基线 §13.6）。

### D2 0x50 快照端点 ABI + 能力位（endpoint ABI + capability bits）
- 12 个语义类（CREATE/EXTEND/DELETE_EXPIRED/RESTORE/LIST/QUERY/HISTORY_OPEN/FREEZE_SET/
  FREEZE_CLEAR/OPEN_WRITES/QUERY_REQUEST/ACK_REQUEST，候选 L52）的 endpoint_type/op 标签、
  magic/version/header_len、字段与枚举。
- 寄存器绑定沿用 §9.6.1（x0 endpoint_cap、x1 请求帧、x2 总长、x3 cap_selector、x4 应答
  缓冲、x5 容量，基线 L4090-4092）还是独立封包；**不得复用** FileServiceSchemaV2 magic
  `0x43594632`/SVC 0x45（候选 L52；V18 ABI）。
- 能力位分配：CREATE/EXTEND/DELETE_EXPIRED/RESTORE/LIST/HISTORY_READ/PROTECTION 等独立位，
  普通 FILE_READ/WRITE/UNLINK 不隐含管理权（I8；V18 ABI 权限表）；真实主体/角色白名单
  （恢复监督者 vs 普通主体 vs 内部维护），权限原子门与恢复代际字段。
- 不新增系统调用号（I7）；黄金反例（越权/旧代际/伪造身份）。

### D3 FileServiceRequest v4 / Reply v3 绑定
- 快照操作如何承载于 v4 帧：op 段扩展 vs 0x50 下独立 endpoint_type；32B 头
  （magic `0x43594651`/abi=4/header_len=32/op/flags/payload_len/request_id/auth_context_id，
  基线 L4090-4096）字段语义；Reply v3 状态码与错误码（E_SCHEMA/E_STALE 旧封包，基线 L5955）。
- 哪些快照操作消耗持久票据/Receipt v4/Index v4，哪些走易失键（基线 §9.6.1 四类持久操作
  模式）；持久请求去重键与水位（V18 的 FileReqKey 36B/64 请求 48+8+8 分区仅作参考输入）。
- staging 预算：v4 每槽 17 页=69632B、全局≤8 槽=544KiB 计业务 RAM（基线 L4096-4100）；
  快照帧（V18 请求≤1024B/应答≤2048B）是否复用该 staging 或独立计账槽，失败不占完成/恢复池。

### D4 迁移证明要求（migration proof）
- v2 只读导出契约（经 `storage.rs` 解码 + 快照管理器只读路径）；全零 512 MiB 新镜像重建
  发布顺序（基线 L3929-3931）。
- 导入连续性证明：保留截止、snapshot_id/槽/槽代际、保护代际、请求水位、BootEpoch、
  SecurityState 各代际**逐项不回退**（I1/I3/I4；候选 §5）；ACL/inode 代际/持久收据合并
  规则；无法证明授权一致 → 拒绝恢复（候选 §5）。
- 禁止无证明可写迁移（I2）；混合格式/身份不符/代际不连续双份 → RECOVERY_REQUIRED/Conflict
  （`file_media_v0199.rs:201-227` 现状）；离线恢复程序重建协议与验收独立交付（基线 L3984-3988）。

### D5 快照预算独立核算（budget carve-out）
- V18 历史输入：68 KiB 管理（句柄 16+冻结视图 24+控制/目录缓存 8+共享位图 16+协调 4）、
  128 KiB CoW 版本记录上限（实测 98 KiB）、48 KiB GC 工作区（复用 160 KiB 事务工作区
  第 24–35 页）（V18 记录 L109-124；候选 L56）——逐项映射到 8 MiB 控制池子预算 / 8 MiB
  进度池 / 10 MiB FrameMeta / 业务 RAM 总账，给出唯一归属，不隐藏新常驻池、不消耗最后
  完成/恢复额度（I5；基线 L3746-3752、L5964-5968；目标 L35）。
- 现有有界工作区作为核算输入：`file_mount_v1.rs:109` 挂载 Workspace≤192 KiB。
- 磁盘空间下限：受保护历史根 vs 业务 ENOSPC；槽满/池耗尽时保持保护下限与恢复额度
  （候选 §7 空间与进度组）；固定容量不互借、周期层至少一个可验证保护点（候选 §3）。
- 参数注册表唯一来源+测试映射：槽数 8（6 周期+2 按需）、周期 6h/48h、保留 18h/144h、
  按需 1h/24h/7d、60s 在线年龄粒度、句柄 112+16、冻结视图 56+8、请求 48+8+8
  （V18 记录 L99-107、L148；候选 §3「待核定候选」——这些值是候选沿用，须 G1 与布局/账本/
  测试窗口共同锁定，非已冻结）。

### D6 保护状态载体与合并规则（security-state merge）
- 保留期/保护代际/写门/开门证明的持久载体：独立 SnapshotProtectionStore（A 候选默认）
  vs SecurityStateStore v3 修订（须批准）；**不得**写入 v2 保留区（基线 L4609）。
- 恢复时 ACL/inode 代际/持久收据合并的确定性规则与拒绝条件（候选 §5；台账 S3）；
  恢复后写门保持关闭、独立 OPEN_WRITES 开门证明（候选 §5；V18 记录 L86-89）。

### D7 黄金向量、独立编解码与验收映射
- 每对象/端点的实际编码器/解码器、CRC/摘要、合法与非法 golden vectors、状态机、平台
  寄存器期望值/读回方法、锁定仿真配置与独立判定器（基线 §13.6 G1 交付，L5957-5960）。
- 127 稳定 ID 保留；候选 §7 新增断言组（COW 历史/权限保留/断电重试/恢复隔离/空间进度/
  双脑负向/端到端）在冻结后映射独立需求追溯；历史原生 FAIL 保留，不重标 PASS（I9）。
- 格式化器初值核定：ROOT_SIZE=128 与 ACL 初始属主 principals[0] 为 fixture 推导、非基线
  固定 wire 初值，须 G1 核定；生产启动接线须签名清单实际属主（目标 L70）。

## 6. 批准路径与边界

1. **本提案 → 用户/设计权威批准**：选定策略（推荐 A）并批准 §4 的前置修订项（基线
   §9.2.1 对象计数/挂载豁免、保护状态载体）。批准前本文件不产生任何规范效力。
2. **批准 → G1 冻结**：按 D1–D7 产出冻结契约 + 黄金向量 + 独立编解码 + 预算证明；
   G1 状态由 NOT_READY 转冻结须附证据（目标 §7）。
3. **G1 冻结 → 实现**：台账 S5（统一介质/ABI）→ S6（原生文件服务）→ S7/S8；任何代码
   迁移另行实施（目标 L76），不在本提案范围。
4. **明确不做**：不修改任何现有设计文档/基线/代码/测试；不新增系统调用号；不以旧卷直接
   重格式化或静默放宽保留期满足测试（目标 L56）；不把历史宿主 PASS/原生 FAIL 重新解释
   为当前分支验收（候选 §7；I9）。
