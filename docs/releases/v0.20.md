# CyxiaOS V0.20 原生单机强化开发记录（WIP，不可宣称发布验收）
 
当前分支为 `CyxiaOS-V0.20`，`VERSION` 为 `0.20.0-dev`。本记录始于 `0e832f6ed145d283bcbf08bd1ae680d04c1c1d4a`（当时代码版本为 `0.19.0-dev`）。当前接线状态见第十一至十八波。
 
## 设计原则

完整目标契约见 [V0.20 原生单机架构设计增补](../design/v0.20-native-local-system.md)，明确覆盖旧最小原型的动态控制核与 D16 双节点章节；设计不代表运行验收通过。
 
- V0.20 固定 C={CPU0} 控制、B={CPU1–3} 业务。第二波完成代码层切换，`control_plane/fixed.rs` 统一引用 `cpu0_v0199` 契约常量，SEC-P/SEC-D/SEC-S 准入及默认 `smp-selftest` 同步迁移。旧动态 CoreSet 路径由 `legacy-coreset` 隔离。后续已有原生固定拓扑机制夹具和启动阶段 TTBR0/PMU 证据。完整原生拓扑及全负载控制预算仍待验收，CPU0 失效时业务核不接任控制核。[V0.20 原生单机架构设计 §2](../design/v0.20-native-local-system.md#2-平台与可信边界)
- 运营 AI 与安全 AI 各只进行观测、辅助分析和建议；独立的身份、邮箱及资源额度不能产生能力、批准、确定性裁决或执行。最终安全拒绝、资源账本、设备/文件确认必须由原生确定性机制完成。
- 所有本地内核基础机制和系统服务享有同等 AI 建议接入地位：观测→建议→独立校验→原生执行→关联反馈，热路径不等待模型。
- 六大安全方向：SEC-P 进程、SEC-F 文件、SEC-M 内存、SEC-N 网络、SEC-D 设备和 SEC-S 系统调用。原型单域主机测试不等于 ARM/x86 原生安全验收。
- 不保留集群发现、远程合同、分布式恢复或 D16 跨节点放置。必须保留独立本地 TCP/TLS、SMP、IPC、文件与设备的本机能力。
 
## 早期拓扑整改记录（第十一波现状见下文）
 
1. `control_plane::fixed::valid_layout` 明确排除 CPU0 作为业务核；新增错误布局的 Rust 负向断言。
2. AArch64 `domain_tasks::begin_control` 和 `verify_control_credit` 只允许 CPU0 拿取/核验控制预算凭证（门控为 `fixed::CONTROL_CPU`，第二波起重新导出 `cpu0_v0199` 契约常量 =0，CPU1–3 均为业务核）。历史口径：基线原为 CPU1|2 双入口，本分支先收紧为仅 CPU1（拒绝 CPU2 的旧控制预算入口），第二波 CPU0 拓扑切换将同一门控落到 CPU0。
3. AArch64 `prototype_runtime::step` 不再进入退休的 CPU2 第二控制工作器。
4. 更新开发版 VERSION 与分支说明；加入本分支针对源码和主机机制的并行 CI 入口、精确源码归档及散列。
5. 默认 workspace 测试入口不再编译历史 `cyxia-cluster-transport`，改为包含 `cyxia-net-transport` 与 `cyxia-local-echo`；旧集群模块 `peer-billing`/`cluster-transport` 已在根 `Cargo.toml` 的 `exclude`（不在 `members`），仅 `kernel/Cargo.toml` 为遗留诊断特性 `tcp-v13-selftest`/`unified-runtime` 保留可选依赖边，**仅完成默认入口隔离，未完成彻底去分布式**。
 
这些变更**只收紧固定核心入口**，还不能据此认定 ARM 70 ms / 100 ms 累计预算超限已被真实修复。必须复测所有必需控制任务、运营/安全 AI、学习/Shadow/Canary、恢复及 broker 计量，保存每窗口预留与实际 CPU 时间、超限和拒绝/降级证据。

## 2026-11-25 第十一波生产路径接线

第十波的异常向量内 `0x50`/`0x41` 建议链及 `0x40` 入口成为第十一波的接线起点。AArch64 `v020-production` 继续使用 CPU0 控制拓扑，并在该启动配置中接入以下路径。

- **FrameMeta** 将链接器划定的常驻页在 EL0 启动前登记并校验守恒，固定保留的 Arena 含 SEC-N 设备池、TCP 缓冲、EL0 guest 页池与 broker 页。显式启用介质暂存时，scratch 设备缓冲区和暂存工作区也纳入登记。动态 DMA pin 仍由设备路径管理，通用页分配器接入仍开放。
- **RecoveryProof v2** 由四个 vCPU 各自单写易失累加器，记录 EL0 同步异常。发布门读取 EL1 持有的暂存检查点对验证事实。启动探针刻意撤去一个见证后执行真实 `0x41`，在 `RECOVERY_REQUIRED` 下拒绝发布。CPU1–3 停止且确认各写者静止后，CPU0 核验代际和事件水位完成接管，并消费保留的证明。角色 11 的持久 `AUDIT_READ`/`AUDIT_ACK` 接管仍因缺少授权的磁盘承载而阻塞。
- **计量** 在 `0x50` 登记和 `0x41` 发布的 bridge 调用外用架构计时器采样，分别记录已计量超限与未计量尝试，并输出最大已计量耗时（ns）。此处提供诊断。生产 `policy_lock`、IRQ-off 强制和全负载窗口预算验收仍开放。
- **SEC-N** 在真实 VirtIO-net 设备上建立 TCP，经既有 SVC `0x43` 转接至 `local-echo` EL0。EL0 的 `net-transport::admission::Admission` 是唯一连接额度账本；guest 经 `0x43` 提交准入收据，broker 以当前连接代际和锁定的源 IPv4 校验。无网卡时启动继续，网络证据保持为空。认证 TLS Echo/Finish 和生产熵源仍缺。

显式启用 `v020-production-media-staging` 时，CPU0 对独立全零 scratch VirtIO-blk 卷运行 v1 格式化、挂载校验和八对象统一地图检查，完整扫描空白 redo 区后才签发暂存 BootEpoch，并经有序 FLUSH 和设备回读确认。EL1 以固定输入运行 FileServiceRequest v4 / ADMIT v3；暂存完成判据同时要求观测到经过鉴权的快照 `0x40` 返回 `EAGAIN`。scratch 卷使用测试清单，仍为 `golden_vector_pending`。签名配置、正式 v1 生产挂载、跨启动持久性、快照后端和正常 EL0 文件服务仍待交付。G1 的策略 A 方向已批准，字节精确冻结、黄金向量和独立编解码仍开放。[G1 策略 A 批准件](../design/v0.20-g1-media-freeze.md)
