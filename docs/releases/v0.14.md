# CyxiaOS V0.14 — development source snapshot

## Version boundary

- Software snapshot: **0.14.0-dev**, branch `CyxiaOS-V0.14`.
- Parent baseline: `CyxiaOS-V0.13@7fcc678d0055cb8b2a97a136cc109996411f1579`.
- Design specification remains **1.3**. Policy, syscall and filesystem ABIs are not renamed or changed by this software version.
- V0.13 is retained without rewriting its history. Existing `v13_*` tool names and evidence symbols identify established contracts, not the software release number.
- This is a source-development release, **not complete prototype acceptance**. No A/T/E status is promoted by the version bump or the source package.

## Included change: A10 fault arming

The prior backend counted WRITE/FLUSH operations immediately after NBD connection. A QEMU management FLUSH during preboot GDB configuration could therefore occupy mutation 1 and trigger `cut=1` before the sole guest resume. The existing native verifier correctly rejects such an observation; its post-resume check remains intact.

The A10 runner now performs:

```
create backend in PREPARE
  -> connect/inject GDB configuration
  -> verify exact configuration readback
  -> arm at an empty, fully acknowledged NBD request boundary
  -> send the sole QMP cont
  -> execute the selected post-arm fault ordinal
```

The new v2 backend capture has two identities. `raw_mutation` is the unchanged, global WRITE/FLUSH ordinal from the beginning of the connection. `mutation` is zero during PREPARE and starts at one after the explicit arm. A read has zero in both mutation fields. Thus `--cut 1` means the first post-arm WRITE or FLUSH, irrespective of whether zero, one or several preparation FLUSH requests occurred. There is no `cut + 1` adjustment and no blanket rule to ignore the first FLUSH.

Arming is bound to the frozen input hash and serialized against complete request/reply batches. Outstanding replies, queued input, a disconnected backend, repeated arming or preparation WRITE fail closed. Preparation traffic and its real completion/ACK/durability records remain in the archive. The independent byte replayer reconstructs both sequences, the empty boundary and all durable bytes. The scope verifier additionally requires configuration readback <= arm <= the real QMP resume request, and rejects armed requests observed before resume.

Arming is **before** first guest execution, not after mount or AI_ACTIVE. Recovery writes remain eligible fault points. The runner still prohibits a clean QMP stop/quit before a cut and kills only its own QEMU process. This change does not make arbitrary debugger reconnects during a fault window safe: unmodeled management I/O invalidates a native trial. Native provenance remains a separate gate.

The guest kernel, disk format, successful FLUSH semantics, before/after-ACK cuts, drop/reverse-half loss policies, CPU budgets and guest deadlines are unchanged. Default backend callers without an arming identity retain the v1 absolute-numbering contract. A v2 input cannot be silently relabeled as a v1 capture.

## Changed implementation areas

| File | Responsibility |
| --- | --- |
| `tools/v13_fault_disk.py` | One-shot quiescent arming; versioned raw/scoped mutation identities. |
| `tools/check_v13_fault_disk.py` | Independent v1/v2 wire and durability replay; strict arm-boundary checks. |
| `tools/run_v13_a10.py` | Freeze `cut_scope=post-arm-v1`; arm only after configuration readback and before cont. |
| `tools/v13_a10_fault_scope.py` | Bind the arm event to the input, readback and resume; retain absolute raw identities. |
| `tools/test_a10_fault_arming.py` | Socket-level backend regressions, durability checks and tampered-evidence rejection. |

The inherited A01 worker-settlement, four-CPU observation, reboot-lineage and VirtIO timeout-ordering changes remain in the branch history. Their earlier results remain bound to their earlier source commits; they are not automatically evidence for this snapshot.

## Validation and packaging

The new regression is run with:

```
python3 -B -m unittest discover -s tools -p 'test_a10_fault_arming.py' -v
python3 -B -m unittest discover -s tools -p 'test_*fault_disk*.py' -v
python3 -B -m unittest discover -s tools -p 'test_*a10*.py' -v
```

These are **host NBD/tooling tests**, not a CyxiaOS native A10 matrix. They cover preparation FLUSH counts 0/1/3, both fault phases, first WRITE and first FLUSH, reply reversal settings, preserved flush/loss semantics, delayed completion, queued requests, repeated arming, preparation writes, raw-id tampering and resume-boundary violations. Synthetic lifecycle records are labeled as parser fixtures and never presented as a native receipt.

`Validate prototype branches` now includes V0.14 and runs the unchanged static/Rust/host/tools engineering lanes. `V0.14 source snapshot` retains the targeted host logs and, only after those checks pass, packages the exact committed source with its commit, tree, SHA-256 and validation scope. Its artifact is `CyxiaOS-V0.14-source-<commit>-<attempt>` and contains `CyxiaOS-V0.14-source.zip`, `SHA256SUMS`, source identities and `validation-scope.json`. The package is not a bootable binary release. CI artifacts have a 30-day retention policy, not permanent archival.

Actual test outcomes must be read from the run for the exact commit; this source document does not predeclare a CI result. Source-only packaging does not imply all engineering lanes or native acceptance passed.

## Evidence migration and remaining gates

Do not resume an old A10 matrix under the changed tool hashes or reinterpret its raw cut numbers as v2 scoped numbers. Keep historical failures, use their matching verifier revision, and generate a new probe/cut matrix for the new contract. The complete native matrix must still establish all A10 assertions, including interrupted recovery and post-ACK cross-endpoint/cache-eviction visibility. No fixed failure is removed from the ledger.

A01 still needs its complete formal acceptance mapping and unresolved historical failures must remain visible. A10 still needs full native execution/replay under the pinned patched QEMU. The formal catalogue at `docs/implementation/v13-requirements.json` is inherited unchanged; no manual PASS is added. Any mandatory FAIL or NOT_RUN prevents declaring the complete prototype accepted, as required by specification 1.3 section 14.5.
