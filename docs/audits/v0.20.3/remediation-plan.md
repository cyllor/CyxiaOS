# V0.20.3 自动整改执行计划

本计划由用户“依据审核意见构建自动任务修复缺陷，直到缺陷全部修复”授权。以同目录findings.json为唯一问题台账，原始基线固定为89f87ec7d480cd2cfc5851cecc079da5b3786459。

## 执行主体与分支

使用一个每小时运行的持续整改控制任务，内部按问题依赖进行多任务分析、独立验证和顺序集成。整改期间唯一可写工作分支为work/v0203-architecture-remediation；用户已追加授权问题修复后自动同步CyxiaOS-V0.20，最终集成按下述闭合门执行；每轮先从远端核对该分支实际SHA、已有PR、CI和台账。目录不存在时重新获取准确仓库，不能把临时目录存在作为唯一前提。

已存在的V0.20生产整改任务和V0.20.2性能任务保持独立。先读它们的实际代码与验证结果，识别共享根因（网络P13、模型P16、G01–G11），仅在本分支择取经语义复核的必要变更，不在两个任务的分支并行写入，也不整分支覆盖V0.20.1优化。

## 每轮必须完成的流程

1. 读取cyxaudit技能及当前基线、审核报告、findings.json、最新提交/CI。取得当前head并检查前轮是否仍运行或已有作者变更；有新head就重新读取，不盲写。
2. 先收集前轮准确SHA的CI结果。已有运行未完成时，推进独立只读分析或不影响当前运行的准备，不用连续推送取消尚未验证的结果。
3. 按严重程度和依赖选择可验证的小任务；资源域没有架构优先级。先写真实反例或行为回归，再做最小实现。不得把仅实现形式检查当作行为证明。
4. 运行所需模块回归、工作区回归、格式、跨编译和对应原生/故障测试。精确记录命令、工具链、源码/构建身份、退出码和原始日志。缺环境时实际修复环境阻塞或列明blocked，不编造。
5. 复审权限、代际、唯一所有权、完成credit、预算、TLB/DMA、redo/FLUSH、不可变历史、UNKNOWN对账与恢复不变量。可用独立专业代理时进行交叉复审。
6. 仅在专用分支提交并以普通快进/预期head保护推送；维护一个面向CyxiaOS-V0.20的累计草稿PR。不得强推、改原始V0.20.3或旧任务分支、发布或部署；只在闭合门通过后自动合入用户授权目标。
7. 同步台账及证据。状态为open/in_progress/awaiting_verification/blocked/closed/reopened；每个closed必须有原判据及相应证据。发现同根因合并，新增问题要给具体条件，风险不能假装成缺陷。
8. 向用户报告本轮实际代码、SHA/PR/CI、通过/失败/未运行、剩余和阻塞。没有实质变化时不制造空提交或重复评论。

## 结束条件

所有本次审核及复审确认的缺陷达到原关闭判据；相关强制验证确实完成；未证实风险得到证据支持的排除或进入已闭合缺陷；不存在影响本次闭合的blocked项。然后读取CyxiaOS-V0.20最新head，保留并整合其他任务和用户更新，解决语义冲突，对最终待合并源码完成受影响回归与必要审核。在真实分支保护、CI和权限允许下自动普通合并/受head保护的快进；不得绕过Required Review。合入后核验目标实际SHA及其CI，通过后发送最终证据总表并暂停本自动任务。用户已明确授权这一同步，无需再次请求一般确认；若真实保护或权限阻塞，报告具体缺项。若只剩物理设备、生产签名授权、真实模型或未决架构批准，保留blocked并等待真实条件变化，不能宣称“全部修复”。
