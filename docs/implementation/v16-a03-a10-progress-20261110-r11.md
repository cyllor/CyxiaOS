## 二、校验器缺陷 1：boot seqlock 前置条件不可满足

`tools/v16_a03_full_frontier.py:stopped_frontier()` 原要求 boot 与 runtime 两个 bank 的 seqlock 均「非零且为偶」，取自 `word(probe[key],16)`。两点叠加使该条件对 boot 恒不成立：

1. `word(raw, offset)`（`tools/v16_learning_archive.py:31`）是 `struct.unpack_from('<Q', raw, offset)`，**offset 为字节偏移**，16 即 word 2；
2. `A01_BOOT_EVIDENCE.0[2]` 全仓仅两处写入（`kernel/src/boot_recovery.rs:130,138`），均在 `boot_recovery::run()` 内——那是 `-> !` 的确定性 SAFE_EXEC 循环，只在启动失败时由 `kernel/src/unified.rs:561,568` 进入。

因此任何**干净启动并抵达 frontier** 的 guest，该字恒为 0，`stopped_frontier` 恒返回 `None`。runner 于是在 live 判定已看到边界后仍反复 stop/cont，64 次后死于 `require(stops < 64,'Full frontier stopped probe bound')`（`tools/run_v16_a03_full_frontier.py:59`）。frontier-11 已在全部 64 个探针上**逐位稳定**保持干净双组边界，却仍因此报 FAIL。

其自身测试掩盖了该缺陷：`tools/test_v16_a03_full_frontier.py` 用 `struct.pack_into('<Q',w,16,2)` 为 boot 与 runtime **同时伪造** seqlock=2，即夹具造出了真实干净启动不可能产生的值，故 12 项测试全绿而生产路径永不可能成功。

修复按同仓既有契约对齐（`v16_a03_focus.py:1080`、`v16_a03_data.py:804`）：boot 只查奇偶（撕裂检测），runtime 查非零且为偶。两个夹具改为真实的 boot=0，并新增回归测试固定该契约（boot=0 放行；boot 为奇、runtime 为 0 或奇均拒绝）。RED→GREEN。

## 三、校验器缺陷 2：QMP transcript 超出通用 JSON 上限

修好缺陷 1 后，frontier-13 与 frontier-15 均 `capture_complete=true` 并抵达边界，却双双失败于 `EvidenceError: JSON exceeds bounded size`。根因：完整捕获的 `qmp-transcript.json` 为 5.61 / 5.93 MiB，超过 `tools/check_prototype_evidence.py:69` 中 `read_json` 的通用 4 MiB 上限。

该上限在此处不提供完整性价值：同一工具已把该会话的原始 QMP 字节流上限定为 128 MiB，并逐行交叉校验 transcript 与原始流一致（`raw_qmp_messages(raw) == [r['message'] for r in rows ...]`）；同仓 `verify_v13_a02.py:94` 对同类 QMP transcript 采用 16 MiB 上限。transcript 规模由 0.1 s 轮询与 ≤600 s 宿主窗口决定，实测 5.5–5.9 MiB，外推上界约 8 MiB。

修复位置经约束分析后选定：**只改 `tools/v16_a03_full_frontier.py`**，新增 `QMP_TRANSCRIPT_BYTES = 16 MiB` 与 `read_transcript()`（保留 `read_json` 原有的 `_pairs` / `_finite_float` / `parse_constant` 语义）。**不可改 `check_prototype_evidence.py`**——该文件在构建清单的 `builder_sources` 中，改动会使既有构建的 `manifest['builder_sources'] == closure(...)` 失配而强制重建；而 `tools/` 不在 `code_source_map`（977 项，0 项为 tools）内，故改 frontier 工具不影响构建有效性。

## 八、偶发失败的根因（四级插桩定位，2026-11-11 完成）

用「证据 bank 通道」探针逐级下钻（**不能用串口**：`try_log` 在 `console_ready()` 时走 `domain_services::enqueue_frame`，Busy/Again 会**静默丢帧**只累加 `LOG_LOSS`；第一版串口探针在确实命中站点的 run 里输出为 0）。探针做法：在 `publish_collection` 中把 `static ERR_PROBE: [AtomicU64; 7]` 的前两个事件发布到 collection bank 未使用的 words 56..62，离线读 `failure-collection.bin`。

| 级别 | 结论 |
|---|---|
| 1 | replay `w[12]=8` ⇒ `learning::Error::Evidence`，由 `owner.rs` `verification_step` 的 `match verify(s) { Err(e) => s.last_error = Some(e) }` 置位（site 5） |
| 2 | 来自 `verification.step(...)`，即 `ReplayVerification::step`（`crates/prototype/src/learning/reward/bounded.rs`） |
| 3 | 两个**不同**站点在不同轮次交替出现：`bounded.rs:1105`（`adoption_body` 的 7 项析取）与 `bounded.rs:1178`（`baseline_start` 的 22 项合取） |
| 4 | `line=1112` = `1105 + 7` ⇒ **析取第 7 项：`i > 0 && a.finished_ns > covered_until`** |

**根因**：`adoption_body()` 中 `covered_until` 由调用方以 `until` 传入，每步按 `covered_until.max(a.installed_until_ns)` 推进；而析取第 2 项强制 `installed_until_ns == snapshot.taken_ns + POLICY_NS`（10 s）。因此第 7 项表达的是**候选续约链必须无缝覆盖**：每份续约都要在前序建立的地平线内执行完毕。宿主一旦停顿，guest 纳秒（源自宿主时钟，`-accel tcg,thread=multi` 且无 `-icount`）就会把 `finished_ns` 推过上一份计划的 `installed_until_ns`，形成空隙 ⇒ Evidence。

`bounded.rs:1178`（`baseline_start` 合取）属同一类：其中 `finished_ns ≤ approved_deadline_ns`、`finished_ns ≤ closing_ns`、`taken_ns < observation_end_ns` 均为时序不变式。该轮次未进一步细化到具体子句（当轮构建早于子句级编码）。

**判断**：校验器行为**正确**。续约覆盖出现空隙，正是 A03 验收标准「动作与实际核心所有权线性化对应」所不能接受的，因此**不应放宽该不变式**。诚实的选项只有两个：在空闲宿主上重跑（frontier 确实可达——本轮共 4 次 VERIFIED），或引入 `-icount` 使 guest 计时确定化（属方法论变更，需明确授权）。

插桩注意：把 `||` 合取改写为保序 `which` 链时必须保持短路顺序——第 4/18 项 `approved_deadline_ns - accepted_ns` 是无检查的无符号减法，提前求值可能下溢。
