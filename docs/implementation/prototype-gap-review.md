## 1. 结论与覆盖范围

本轮完成全架构要求到现有执行路径的映射，深入复核控制面/集群的授权、防重放、故障恢复和资源账本，以及桌面构建与 POSIX 文件标志路径；修复 8 类具体缺陷，增加反例和回归测试。它不是“547 个已跟踪文件逐行穷尽审计”，也不是整机安全认证。未修改生产启动拓扑、AI 模型、资源上限或集群成员资格。

既有代码已经有真实单核 EL0 进程、地址空间/共享页、Unix IPC、VirtIO 图形/输入/块设备、RAMFS 检查点及本地整数模型；不能把系统描述成空壳。另一方面，新 control_plane/cluster 库仍未接入生产启动、调度和网络路径，不能据主机测试把多核隔离或原生联网集群标为完成。

本轮修复在工作副本形成补丁，远端主线未被本轮改写。运行收据、补丁和源码散列随审计交付包提供。

## 3. 已修复的代码缺陷

P1 表示接入生产执行前必须关闭的授权/正确性问题；当前库尚未连接真实远端执行路径，以下不能称为已经存在的线上远程攻击。

| ID / 严重度 | 基线缺陷与反例 | 实际修复与位置 |
|---|---|---|
| FIX-01 / P1 | `Endpoint::begin` 只检查安装后的 fence；`GrantIntent` 尚未持久授予，或 Ledger 已 `Revoking` 但端点未关闭，仍能获得执行 Permit。 | `cluster/endpoint.rs::begin` 必须传当前 Ledger 并再次调用 `execution`；同时检查精确 token、Granted、未中毒/未待恢复。任务启动和全部调用点同步更新。 |
| FIX-02 / P1 | 存储写成功但 ACK 丢失后，`Book::query` 返回旧 RAM 的 Prepared，`Ledger::used/status` 可能输出偏低额度或旧状态。 | 三个只读入口在 poisoned 时返回 Reconcile；`needs_reconcile` 不以旧 RAM 是否认识新 ID 为前提。恢复必须重读持久记录。 |
| FIX-03 / P1 | 每笔合同分别符合模型额度，却能在同一 subject 下重复使用额度，例如两笔各 20 页均通过 30 页策略。 | `contracts.rs::prepare` 对同 subject 所有未释放额度累加，再检查 AI 预算；物理总账另行检查。该修复不替代实际 CPU/I/O 运行计费。 |
| FIX-04 / P1 | 相同双 nonce 的 FormationID 可以在下一配置 epoch 签署不同摘要；覆盖当前配置后更早绑定也丢失。 | `membership.rs` 持久保存最多 16 个绑定，跨重载拒绝冲突；新配置必须先持久 Isolated，事务不能隐式替换；满额拒绝而非遗忘。 |
| FIX-05 / P1 | 提交回执只保存最近一个 operation_id，`A(v1)→B(v2)→A(v3)` 能绕过旧操作去重。 | `replication.rs::finalize` 持久保存最多 16 个提交的操作/版本/双签名；拒绝非相邻复用；一致旧请求返回已有结果；容量用满拒绝。 |
| FIX-06 / P1 | 已报告 CPU 故障却传入较旧时间戳时，fault 先返回 Clock，归属表仍允许故障核派发。 | `control_plane/manager.rs::fault` 与 `cores.rs::fault` 使用当前最大可信水位先隔离，普通迁移仍拒绝倒退；不延长任何租约。 |
| FIX-07 / P2 | 普通创建文件或目录的 GETFL→SETFL 往返返回 EINVAL；创建标志还混入共享文件状态。 | `posix/src/lib.rs` 不保存一次性创建/截断标志；SETFL 接受已知不可变位但仅改变 append/nonblock，不改访问模式或 descriptor CLOEXEC。 |
| FIX-08 / P2 | 原生桌面 CI 的 Mesa C++ 依赖下载没有传 `online=True`，实际触发 `choose exactly one of --online or --offline-file`。 | `tools/build_mesa.py::target_cxx` 仅在显式 fetch 分支传入联网授权；保留固定源、hash 校验与 offline 行为。 |

复现先于修复：集群 7 条反例、控制面 1 条、POSIX 2 条均在基线实际失败；Mesa 新测试中的联网分支在基线失败，禁止隐式联网分支原本通过。失败日志随交付保留。再增加 8 条集群历史/恢复/兼容边界及 1 条共享文件描述符测试。

原工作区回归发现一条旧断言期待 GETFL 带 O_CREAT，现明确修正该期望；共享 offset、引用生命周期、unlink 后可读和父子描述符状态检查全部保留。文件访问模式与创建位不能通过 SETFL 获得新的权限；依据 POSIX fcntl/open 的 access/status/creation 分类，而非删除测试规避错误。

## 4. 破坏性持久化变更：必须明确处理

仅成员记录（kind 1）和提交历史记录（kind 6）的存储 schema 升至 2。旧格式缺少完整 FormationID 绑定或历史 operation_id，自动迁移无法凭空补齐。新代码返回 `Error::Version`；没有自动初始化、删库、重置 BootEpoch 或生成新 ClusterID 的分支。

**已有 v1 状态不得直接升级运行。**应先冻结新授权并保留旧状态，设计并验证离线历史补齐/对账迁移。该迁移工具和生产升级测试本轮未实现。原生持久化后端本身也仍待接入。其他记录类型、签名报文格式本轮未改变。

新增的 16 条历史容量是有界安全限制，不是长期运行方案。成员事务、提交记录、原有合同/任务终态均不能无条件删除；安全 GC 需要证明所有旧消息/引用不会重新生效。本轮未实现自动回收或跨节点所有权接管。

## 7. 新增证据门禁

`tools/check_prototype_evidence.py` 校验全部81个唯一ID、两份规范散列、合法状态、代码路径；运行 PASS/FAIL 必须带绑定本次源码树的收据，并校验镜像/模型/动作Schema/环境/事件/判定器/复现脚本的文件散列，以及场景需要的1或2台四vCPU原生客体标识。拒绝 host-unit-test、旧树、缺失/篡改文件、符号链接、路径逃逸、JSON重复键和删减分母。

主机 CI 增加目录完整性步骤并保留报告；它不会运行原生验收或修改要求状态。结构检查通过只表示目录/引用有效。`--release` 只在所有强制项有合格 PASS 收据时返回0；当前目录是79 BLOCKED、2 NOT_RUN，返回2，符合拒绝系统发布的预期。证据散列不证明运行真实性或信任根；输出始终注明 `runtime_truth_attested=false`，仍需独立核验判定器和原始轨迹。测试中的合成收据只验证检查器逻辑，不是原生证据。

使用构建产物对应的源码树运行（不要用无关旧提交代替）：

```sh
python3 tools/check_prototype_evidence.py --source-tree <tested-git-tree>
python3 tools/check_prototype_evidence.py --source-tree <tested-git-tree> --release
```
