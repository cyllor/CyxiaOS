# COSMIC 启动任务归因（2 GiB，2026-11-20）

当前测到的最大串行内核开销来自 **cosmic-comp，其次是 cosmic-panel**。首画面之前，合成器的同步着色器初始化是最长的已标记阶段；首画面之后，合成器仍持续触发昂贵的地址空间准备/撤销，与面板、时钟的启动共享 CPU0 服务路径。

正常会话两轮测到背景在 32–34 秒出现，时钟在 101–107 秒出现。内核到命令行仅 0.40–0.67 秒，D-Bus 就绪约 0.33 秒。启动延迟集中在桌面链路。

## 环境与测量边界

- 同一镜像：`artifacts/v017-os-cosmic-2g-v1/boot.bin`，SHA-256 `5dfa0ffa19ce9e1a4c1f7ba6cac3ac4de45446db6cd1504eedb24e46919c1009`。
- 相同用户程序目录：`artifacts/v017-native-pointer-motion-catalog-v1`。合成器 ELF SHA-256 `104c71be5dc097e20b62f4d50368ee0d8478ab970701320c16e736f19582354e`。
- QEMU TCG、4 vCPU、2 GiB、VirtIO GPU 1024×768。三轮 QMP 均返回 `base-memory=2147483648`、`plugged-memory=0`。测量期间没有构建或其他测量 VM 并行运行。
- 桌面时间起点是发送 `posix exec cosmic-session`；直接合成器对照以 `posix exec cosmic-comp` 为起点。两者都先启动真实 `dbus-daemon`。
- 每约 2 秒获取实际 VirtIO scanout。时钟区域检测连续两帧成立，并人工检查两轮首个候选截图，均可见真实日期时间。时间存在约 2 秒截图间隔误差，不能作为精确的首像素时刻。
- `posix list` 的 `space_prepare_ns`、`space_retire_ns` 是内核 HPET 累计墙钟，**不是每进程 CPU 用量**。下表的占比只占已测地址空间开销，不能当作 CPU 利用率或总启动时间占比。
- 进程名由镜像实际 PT_LOAD 页数加主线程栈页数匹配，另核对保存的 PC 属于对应 ELF 可执行段，未固定假设时钟 PID 为 8。

## 首画面阶段：合成器着色器初始化最长

直接合成器对照保留相同真实 ELF、EGL/Mesa 和真实 D-Bus。19 个一次性阶段标记均被捕获；重复的相同串口标记按阶段去重。

| 合成器阶段 | 墙钟耗时 |
| --- | ---: |
| State 初始化 | 1.799 s |
| EGL display 初始化 | 0.405 s |
| EGL context 初始化 | 1.644 s |
| Glow renderer 初始化 | 2.347 s |
| **init_shaders** | **16.807 s** |
| 首次 render | 0.882 s |
| 首次 readback copy | 0.024 s |
| 首次 readback map | 0.014 s |
| 首次 tile submit 调用 | 0.031 s |

首次完整 scanout 的阶段标记在合成器阶段时钟的 27.760 秒出现。阶段时钟始于首次 State 初始化标记，区别于宿主发送启动命令的时间。表中未覆盖的间隔仍存在，首次 tile submit 返回也不代表所有 tile 已完成。

`src/backend/cyxia/mod.rs:531` 至 `:533` 将 `init_shaders` 放在输出注册和输入/render 定时器注册之前。`src/backend/render/mod.rs:402` 开始依次创建 outline、rectangle、postprocess、clipping、shadow、blur 等 shader。16.807 秒包含应用执行、系统调用及内核开销，不能解释成纯 shader 编译 CPU 时间。采样 PC 在初始化期间命中 `mmap`/`munmap` 包装函数。

该对照用于分段归因，不可把 28 秒空背景当作正常会话就绪，也不能把与正常时钟的时间差全部记给面板。

## 首画面之后：空桌面合成器仍持续放大串行内核成本

直接合成器对照的第 30.005–45.015 秒，完整首帧早已提交，无面板和时钟：

- 3,100 次新增系统调用，同时新增 3,100 次地址空间重建，约 **206.5 次/秒**。
- 新增地址空间准备 6.768 秒、撤销 1.263 秒，合计 **8.031 秒**。
- `waits`、`wakeups` 均未增加，进程持续处于 Running；末次保存 PC 命中 `__clock_gettime+58`。

这证明合成器的持续内核往返在没有桌面客户端时也存在。正常会话第 45、60、90 秒的合成器 PC，以及第 60、90 秒的面板 PC，同样命中各自 ELF 内的 `__clock_gettime+58`。这只是最后一次返回位置的采样，**没有系统调用直方图，不能声称所有调用都是读时钟**。

对应代码路径：

1. `kernel/src/desktop/user/parallel.rs:68` 的 `prepare_job` 调用 `prepare_space`；CPU0 先准备各 AP 的运行上下文。
2. `kernel/src/desktop/user.rs:1886` 的 `prepare_space` 每次调用 `build_space`，重新发布可执行镜像、heap、共享内存映射。
3. `kernel/src/desktop/address_space.rs:213` 的 `begin` 创建新的硬件地址空间；`parallel.rs:337` 起在所有 AP 返回后撤销所有 root，再处理系统调用。
4. `kernel/src/desktop/user/linux.rs:1350` 的 `ClockGettime` 即使只是读取时间，也经历上述入口/返回边界。
5. 选定合成器源码 `src/backend/cyxia/mod.rs:65`、`:568` 注册 8 ms 输入/render 定时器，`tick` 会读取输入、查询当前时间并推进 presentation。它是持续调用的一个可见来源；本次未定量拆分各 timer、线程及 syscall 的贡献。

因此，页表工作是多个任务共同承担的启动瓶颈：大镜像任务频繁返回内核后，CPU0 重复处理映射，面板和时钟的后续推进也需要经过这个串行边界。8.031 秒是实测映射开销，不能直接承诺优化后能节省同样秒数。

## 优化顺序与剩余不确定性

1. **优先降低合成器、面板每次内核往返的地址空间成本。** 研究保留稳定映射、仅对实际 VM 权限/映射变化更新的机制，必须保留跨 CPU 驻留、别名权限、W^X、共享 backing 生命周期约束。当前实现每次执行都会重建，读时间等轻量调用也付出大成本。
2. **再拆分合成器 16.807 秒的同步 shader 初始化。** 进一步量化各 shader 与分配开销，再评估正确的缓存/初始化安排。
3. **继续拆分面板及其时钟子进程的初始化。** 第 90 秒可归属的面板映射成本排名第二；尚无逐线程应用执行计时，不能把背景到时钟之间的全部 69–73 秒归给面板自身计算。

正常日志另有缺失可选应用的 ENOENT、panel/notifications 连接错误、EGL driver 探测失败后回退等记录。当前没有证据把这些日志中的某一项当作百秒级阻塞超时；通知服务第 60 秒后系统调用计数保持不变，不能仅凭报错把它列为首要性能任务。
