# Candidate initial execution custody

The previous native archive retained candidate trial 4 initial 457 as Applied
851.264992 ms after its original snapshot. Its later publication 458 was timely.
These are separate obligations; later success cannot repair the initial side.
Candidate 6's absent adoption history remains separately unattributed.

`Root` now retains one fixed candidate-initial projection. Only the actual
`Executor.publish` path, after its original scope commit and before Desired
installation under the same control gate, supplies the first effective stamp.
The first immutable ApplyId latch and this cache are created together. Missing
stamp means no hint; it does not add a publication error or authorize execution.
Later publications do not replace either initial identity.

The actual `Option<CandidateInitial>` size is bounded to 128 bytes at compile
time and conservatively added to the existing workspace report. The 1 MiB
limit remains unchanged. This accounts for this added resident cache; it is
not a claim that the entire preexisting Root is included in that formula.

The existing gate-release projection requests progress only for a Running
candidate with no fault or close, first-ready scope, matching token/owner/boot,
family/target, complete initial ApplyId, first snapshot time/sequence and a real
nonzero stamp. Pending and Unknown retain execution custody. Control's actual
poll updates this cache after final state/deadline conversion, including
pre-executor rejection, before fallible Registry reconciliation. Applied and
Failed cannot be resurrected by delayed updates. All initial reset paths clear
the cache. Baseline and restoration reasons retain their existing rules.

Owner Activate also requires actual publication before business activation.
An unpublished candidate returns `Ok(false)`; baseline retains its original
publication retry. Read errors propagate. Binding capture/history or receiving
`on_first` is insufficient to start work.

The hint uses the existing nonreentrant helper and fresh service pieces. It
introduces no new pump, arrival, task or retry loop. Replay and one bounded
admission each need their own reservation; an old bill or denied credit prevents
the next piece. First snapshot, 50 ms execution bound, original requests and
deadlines, 100 measurement arrivals, observation and drain windows stay intact.
The cache grants neither publication nor execution authority and cannot turn a
late real receipt into a timely one.

The actual-source host regression covers native precommit through the real
post-commit hook, Root publication/projection, exact Owner Activate arm, Control
poll including deadline and pre-executor Stale, real Task settlement/Scheduler
policy receipt, and the existing helper/CAS/credits with real warm, submission
and admission. Its paid chain keeps Owner/capture and hardware as explicit
facades; it manually forwards a verified Scheduler receipt to the cache. The
separate Control chain tests the actual forwarding hook. The precommit test
uses a counted commit facade and truncates subsequent Desired writes. These
boundaries do not establish an end-to-end native result or WCET.

The initial behavioral RED demonstrates both missing candidate priority and
business activation before publication. Negative controls remove publication,
state-update, gate-release, admission and progress hooks; pass no actual stamp;
move state update before deadline conversion or behind executor entry; permit
terminal resurrection; remove publication or reentry guards. Each must fail its
named behavioral assertion. Native validation and full prototype acceptance
remain independent gates.
