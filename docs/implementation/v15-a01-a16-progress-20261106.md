## 双节点：两次原生执行均失败，根因尚未确定

两次运行使用同一镜像、认证 QEMU、wallclock、MTTCG multi、180 秒上限及 `--reconnect`。
首轮与 Host harness 并发；第二轮在大型编译和 Host suite 结束后运行。

| 尝试 | READY 观测 | 最终结果 |
| --- | --- | --- |
| native-pair-normal | 两端约 129 秒 | 180.143 秒，`TimeoutError: two-guest TCP execution deadline` |
| native-pair-idle-attempt2 | 两端约 52–53 秒 | 180.125 秒，同一超时 |

两轮都完成四核上线、BootEpoch 持久化及认证会话，但未完成任务/结果/ACK/关闭闭环。
两端 sealed dynamic 记录均只有一次扩核，缺少返回迁移；独立回放均拒绝 `missing dynamic 1→2→1`。
空闲条件改善了启动/READY 时间，却没有闭合协议，不能把首轮失败仅归因于 Host 并发。
会话退出记录包含 Driver 的 unit error，当前有限记录不足以还原其完整原始输入与 authority 状态。

按 diagnosing-bugs 的反馈环要求，本轮没有依据这些观测猜测根因或修改生产实现：

- 已重复运行真实原生失败，并保留全部原始串口、PCAP、停止后内存和错误结果。
- 冻结记录可秒级判红，但源代码修改不能改变旧记录，因此它不是可验证修复的实际触发器。
- 直接编译生产 Driver 的三个定向测试通过，其中真实签名流能完成 READY、任务及结果保管闭环。
  它们绕过实际 runtime 的 TLS、OP_POLL 和 broker 调度，不能冒充本次超时的回归。
- OP_POLL 提取 harness 的重复工作断言为红，但网络是 stub，尚未证明与本次超时存在因果关系；未据此修复。
- 完整 `runtime::run` 在 host test 配置下被排除；现有 PCAP 是加密流，终态记录也没有完整 broker 回复、
  时钟、partial IO/AGAIN 及明文 Driver 输入序列。下一步需建立这个真实边界的可重放输入/时钟 seam，
  才能将本次症状缩成秒级回归，再提出和验证根因预测。

当前正式 A12–A14 仍为 NOT_RUN；失败的局部探针不会被转换成正式 PASS。
A10 完整矩阵另有固定 1920 秒及 21720 秒场景预算，本轮未以缩短超时的探针冒充完整执行。
