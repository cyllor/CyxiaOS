# Independent interactive xdg-shell clients

[`smithay_interactive_client.c`](../../user/ported/smithay_interactive_client.c)
implements two independent AArch64 libwayland clients for native interactive
move and bottom-right resize. The compositor spawns separate processes with
argument `1` or `2`, a separate Wayland connection on descriptor 3, and opposite
ends of a private Unix stream on descriptor 4. Existing multiwindow and
single-window clients remain separate tests.

This bounded profile verifies physical pointer authorization, two move steps,
two resize steps, activation, real configure acknowledgements, new shared
buffers, pointer-grab focus and close fallback. It does not establish a complete
COSMIC session, arbitrary application compatibility, decorations, popup grabs,
other resize edges or a guest-tested cancellation path. Cancellation and
geometry bounds have separate protocol-independent server unit tests.

interrupted writes. The client host suite contains ten tests.

## Actual pointer authority and peer exchange

A initially commits its mapped buffer and then requests `move(serial=0)` on
the same ordered Wayland stream. The server must reject this forged serial.
No synthetic input is generated by either client.

On the real left-button press, A transmits the actual nonzero
`wl_pointer.button` serial to B over descriptor 4 as four little-endian bytes.
B requests a move of its own toplevel with that exact live A serial. A normal
Wayland synchronization callback proves the server processed the foreign-owner
request before B echoes the same serial to A. Both clients close their peer
descriptors after this exchange. A validates the returned serial against its
actual press before requesting the legitimate move.

After the physical left release and pointer reentry, A resubmits the old serial.
A second real synchronization callback precedes an ordinary repaint using
the stored left-button code 272. This frame must retain the moved origin even
though its latest configure ACK predates the move. The right-button resize
request uses its own fresh physical press serial and bottom-right edge 10.

Receipts correlate each request by client, local request index and actual
serial. `PEER op=sync` is emitted inside B's real callback, and `STALE_SYNC`
inside A's actual stale-request callback. The verifier must also require the
server's respective rejection and actual pointer authority; client declarations
alone do not prove authorization.

## Configure, frame and input contract

The 128×96 canvas starts with A at `(8,8)` and B at `(40,24)`, both 64×48.
B starts on top with keyboard focus. The pointer starts at `(16,16)`, in A's
exclusive region. A's left press activates and raises A. Two motions of
`(+8,+4)` move A first to `(16,12)`, then `(24,16)`.

After move release and the ordinary repaint, a right press starts resizing.
The initial resizing configure is 64×48. Motion `(+8,+4)` produces 72×52;
motion `(-4,+4)` produces 68×56. The right release requires a final 68×56
configure with the resizing state removed. Q closes A, D updates the surviving
B window, and Q closes B, leaving a black canvas.

| Client | Configure `(width,height,activated,resizing)` sequence |
| --- | --- |
| A | `(64,48,0,0)`, `(64,48,1,0)`, `(64,48,1,1)`, `(72,52,1,1)`, `(68,56,1,1)`, `(68,56,1,0)` |
| B | `(64,48,1,0)`, `(64,48,0,0)`, `(64,48,1,0)` |

| Client/frame | Dimensions | Physical pixel seed | Presented scene |
| --- | --- | --- | --- |
| A/0 | 64×48 | 0 | 0 |
| A/1 | 64×48 | 272 | 4 |
| A/2 | 64×48 | 273 | 5 |
| A/3 | 72×52 | 273 | 6 |
| A/4 | 68×56 | 273 | 7 |
| A/5 | 68×56 | 273 | 8 |
| B/0 | 64×48 | 0 | 0 |
| B/1 | 64×48 | 32 | 10 |

Every configure's actual serial is acknowledged before the corresponding
buffer commit. Activation changes and moves do not themselves repaint; A's
post-move repaint requires the stale-request synchronization, each resize frame
requires an actual configure, and B's health frame requires D release.

During a compositor grab, pointer focus is cleared and the clients must receive
neither motion nor button release. A accepts exactly two button presses and
three pointer enters, at local `(8,8)`, `(8,8)`, then `(12,16)`, with two normal
leaves. B accepts no pointer event. A accepts only Q press/release after its
sixth frame; B accepts D then Q press/release. Keyboard input requires actual
keyboard focus, activation, non-resizing state and the correct xkb translation.
Unexpected, duplicate, unfocused or out-of-order input fails immediately.
Optional own-close leave events are bounded and recorded separately; B can
never receive an own-close pointer leave.

## Shared buffers and lifetime

Each frame creates a new sealed memfd with a writable shared mapping. The client
creates the real SHM pool and buffer, destroys the pool, closes its local fd and
completes a server roundtrip before writing any pixels. Physical scanout can
therefore pass only with actual shared pages, not an import-time pixel copy.
The RGB formula includes client identity, frame index and the received physical
input code. Each real frame callback is counted exactly once, and every buffer
remains mapped until its genuine release event.

After final Q release, each client requires one `xdg_toplevel.close`, commits a
null buffer, synchronizes, destroys all released buffers, unmaps their pages and
destroys roles in protocol order before disconnecting. A requires six frames,
callbacks and releases, two key events, two button presses, four move/resize
requests, and six configure/ACK pairs. B requires two frames, callbacks and
releases, four key events, one foreign-owner request and three configure/ACK
pairs. Both require the complete peer serial exchange and exactly one peer fd
close. Runtime verification additionally needs independent QMP input, all twelve
scanout scenes, server authority and geometry, both live process identities,
clean exits and resource reclamation.

## Native runtime evidence

The final
[`smithay-interactive-runtime-r0`](../../artifacts/smithay-interactive-runtime-r0/summary.json)
completed three independent single-core ARM QEMU boots successfully. Its summary
SHA256 is `1e2418b87afb3aaf9cb97a2903954501155318da562cc6cbb6ecee65be7f9d58`.
Across those boots, the verifier checked 36 physical scanout scenes and 442,368
pixels, 42 actual QMP input commands, 27 configure/ACK pairs and 24 real buffer
commits. Every capture passed on its first attempt. Each boot included both live
client PIDs, all three authorization rejections, eight frame callbacks and
releases, both clean client exits, and complete object/grant reclamation.

The independent
[`raw evidence audit`](../../artifacts/smithay-interactive-audit-r0/review.json)
also passed with no findings. It reconstructed console text from 528 CRC-checked
UART frames per boot, checked all 207 protocol records fit single atomic writes,
repainted each physical screenshot independently, and checked actual pre-input
UART prefixes for client dispatch barriers. It also verified QMP completion
ordering, all 19 distinct configuration/native-input serial allocations per boot,
490 provenance bindings and 118 kernel source identities.

There were 108 completed local-AI display admissions across the three boots,
with no CPU guard selections or display guard admissions. This evidence covers
the bounded native interactive-window profile described above; it does not
establish a complete COSMIC desktop session.
