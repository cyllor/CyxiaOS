## 后台维护修复的反馈与因果边界

C3 新模式4产生真实失败：117 次成功 WRITE 后，同一 handle/offset/65536 字节 payload 连续91次 completed WRITE 返回 EAGAIN，触发原有214上限。受保护回复逐行重放锁定该症状，未删除原行。它不是六小时预算耗尽，也不能只凭无新媒体 I/O 或旧发布 bank 判定整机停滞：成功的内存 WRITE 可以在没有新落盘时继续发生。

随后构建了实际 Timers、原样 `domain_services::service/with/Guard/due`、原样 `mechanism_progress` 调用顺序及受控耗时端口的反馈。两次 progress 推进计时器所有者时间后，维护尾部仍用入口旧时间 `arm_timer`，得到真实 Stale；此前 swap(false) 已消费唯一待办，尚未成功设定未来 timer，刷盘入口不再到达。最小反馈两次 RED；仅移除耗时推进的控制 GREEN。原始完整 Client+Broker+FS+Journal 场景也 RED/214。

修复仅在维护使用点读取当前时间，arm/owner/overflow 失败时恢复未处理待办并返回原错误。保留原10ms周期、CPU信用起点、预算、2s等待、90次上限及原硬刷盘错误的未来 timer/重试语义。完整 host 场景和9项真实计时器/所有者错误恢复回归通过；独立审查运行冻结二进制9/9通过。host 不模拟物理 CPU 计费或 root byte/DMA 层；新的 C4 原生通过验证了本次真实路径，但新 UUID/nonce/调度历史使其不是严格单变量原生消融，不据此宣称旧214只有一种可能原因。

## 其它诊断结果
