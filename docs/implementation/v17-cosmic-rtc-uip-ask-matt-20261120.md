# COSMIC 内核与桌面性能诊断：RTC 瞬态恢复

本轮使用 `ask-matt` 路由到 `diagnosing-bugs`。两项性能候选经真实客体测量
后均回退，保留已有映射与回收优化。最终新增生产行为是 PC RTC 短暂更新
窗口的有界重试；本轮不宣称获得新的可靠桌面提速。

## 已定位问题与修复边界

`CLOCK_REALTIME`、`gettimeofday` 等通过 PC `realtime_seconds` 读取
MC146818。低层解码器在 16 次即时采样均遇到更新窗口时返回 Busy，包装器
立即映射为 EAGAIN。确定性回归让更新窗口恰好覆盖首轮采样、下一轮恢复，
实际原包装器返回 `Err(Again)`，而有效新时间已经可以读取。

现在仅在 Busy 后重新采样真实 CMOS，每轮前检查 1 毫秒 HPET 期限，并有
1024 轮工作量上限；单轮硬件采样不会被中断。成功样本沿用原路径，不读取
重试计时器；不缓存、猜测或推进
墙钟值。持续 Busy、无效数据、设备不可用和非 CPU0 的原错误保持不变。
HPET 停止或倒退时也由工作量上限保证结束。CMOS 端口始终只读，NMI 策略
不变；初始化失败仍可按需重试。

新增实际包装器用例验证短暂更新后读取的是新秒值、持续忙、停止的计时器、
时间截止、正常路径没有额外计时器访问，以及恢复后的真实硬件错误。原四项
硬件错误和 CPU0 边界用例保留。当前 9 项 PC clock 与 4 项 RTC 解码测试通过。

最终九项测试另外链接实际 POSIX 库，在归档的原包装器上重放：7 项通过、
2 项失败，分别为短暂 Busy 后读取新时间、以及 Busy 后无效新样本的硬件
错误传播；新包装器九项均通过。编译成功后才验证指定断言失败，保存生成
源码、原包装器、实际 rlib 与测试二进制摘要，避免把链接失败当成红灯。

## 性能候选与未解决项

| 候选 | 宿主测量 | 真实客体结果 | 保留决定 |
| --- | --- | --- | --- |
| 按字块预查封存状态 | RX 映射约快 10–12% | 两轮归一构建指标均略慢；交互合计 66.108 / 75.620 秒，对照 65.656 / 61.954 秒 | 回退 |
| 独占 alias 计数快捷路径 | RX 映射约快 10%，回收约慢 48% | 约 88 秒时钟进程退出 134、Rust 时间读取 panic，未完成交互 | 回退 |

详细负面结果分别见[封存预查实验](v17-cosmic-sealed-range-ask-matt-20261120.md)
与[计数实验](v17-cosmic-alias-counter-ask-matt-20261120.md)。没有把调用次数
减少当成速度结论，也没有删除失败样本或扩大资源上限。

实际 panic 的最后位置在 Rust Unix 时间读取中。该版本会对 `clock_gettime`
结果执行 `unwrap`，但原串口未保留具体 errno，不能据此确认 RTC Busy 就是
那次失败原因。带失败标签的原版已重新完成两轮真实交互，未触发 Busy、
错误 CPU 或 panic，因此该次 panic 的因果仍未解决。
参见 [Rust 固定版本源码](https://github.com/rust-lang/rust/blob/59807616e1fa2540724bfbac14d7976d7e4a3860/library/std/src/sys/pal/unix/time.rs)。

基线逐进程分析显示，合成器与面板占本轮地址空间构建 HPET wall 的约
78.5%；交互期间七个原进程重建约 2.2 万次。下一步仍应测稳定映射的重复
构建与调度，根复用需要先证明映射变更、驻留、W^X、shootdown 与 backing
回收的完整协议，当前没有引入生命周期变化。

## 验证范围

宿主硬件边界夹具只替代端口 I/O、CPU 身份与单调计时器；RTC 解码与内核
包装器来自实际源码。PC clock 红灯是实际结果断言失败，6 项通过、1 项
失败；新增边界后绿色版本为 9 项通过。没有用修改生产输入制造红灯。

本轮一度因恢复源码时保留旧 mtime，使 Cargo 复用上一候选的测试二进制。
该 293 项结果明确作废，后续改用构建源码内容哈希隔离 target，并在检查后
重新比较源码。直接 rustc 生成的 runtime 夹具与按内容命名的内核构建不受
该问题影响。当前结果为 291 项架构/PC/kernel-core、9 项 PC 时钟、4 项 RTC
解码以及 48 项实际 runtime 用例通过；4 项解码也包含在前述架构检查中，
不额外合并计数。最终镜像原生烟测 `OS_NATIVE_PASS`。

本轮没有重跑全工作区及全量 Python。格式检查仍失败，输出 37 条路径、
对应 36 个物理文件，路径集合与上一轮一致。历史 Python 平台/夹具失败见
[检查缺口清单](v17-cosmic-retire-regression-gaps-20261120.md)，不能据此宣称
当前全仓 CI 通过。

真实平台为 ARM/macOS 上的 x86 QEMU TCG，4 vCPU / 1 GiB，129 项桌面输入
固定；它不代表物理 PC 的耗时。原始驱动的 45 秒必要色条替换和 15 秒交互
期限保持原值。语义首帧、完整 OS 与 COSMIC session 不由像素阈值证明。

最终镜像为 `artifacts/v017-os-ask-matt-clock-fix-v1`。与本轮初始镜像的
构建源码差异只有 `kernel/src/platform/pc/clock.rs`；测试代码另行绑定。
相同原驱动、180 秒观察、真实输入设备完成两轮开关，单位为秒：

| 操作 | 初测 | 复测 |
| --- | ---: | ---: |
| 打开日历 | 17.105 | 18.255 |
| 关闭日历 | 19.705 | 15.266 |
| 再次打开 | 19.140 | 21.375 |
| 再次关闭 | 11.744 | 19.072 |
| 四次捕获区间之和 | 67.694 | 73.968 |

两次均为功能 PASS、15 秒整体期限 FAIL。没有异常退出，原核心进程和时钟
存活；每次关闭后都恢复本轮原始 12 个共享对象、105 页、20 个映射及完整
引用/授予基线，容量仍为 16 槽 / 4096 页。该时间和不含启动观察和区间间
查询，不能当成完整 VM 运行耗时。

实图已检查月份网格、20 日高亮和设置文字。初测捕获的设置入口底边仍有
裁切，复测底边完整，不能据此声称两次均是完整语义帧。45 秒截图仍只有
背景和指针，尽管原色条替换必要条件通过。没有修改旧驱动的判据或结果。

末尾追加同一原版镜像的对照，以观察构建和回收指标随测量时间变化的情况。
这些是七个原存活进程的累计 HPET wall 差值，不是 CPU 计费。本轮没有新的
可靠提速结论，稳定性修复也不能被表述为桌面加速。

末尾原版对照功能与共享回收通过，四次交互为 21.266 / 13.398 / 18.442 /
14.362 秒，合计 67.468 秒，15 秒整体目标仍 FAIL。同一原版的归一构建 /
回收指标由早先 977.6 / 262.5 µs 变为 1106.7 / 293.7 µs，说明未改动的
路径也有明显运行波动；不能把全部差异单独归因于 RTC 修复，也不能据此
证明它更快。完整数据保留在 `closing-control-summary.json`。
